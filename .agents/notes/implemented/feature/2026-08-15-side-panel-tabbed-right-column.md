# Agent Note: Side panel — tabbed right column with a launchpad

Status: implemented

English | [中文](2026-08-15-side-panel-tabbed-right-column.zh.md)

## Problem

The web client had no durable right-side working surface: tool-call details occupy a narrow transient column, `/btw` answers render as an inline command card, and a terminal had nowhere to live. The ask was a browser-style side panel — its own tabs, a launchpad when empty, draggable width, and extensibility for future apps — placed behind a rightmost toggle in the session header.

## Decision

The panel is split along the frame/plugin seam the slot system already draws:

- **[ui-layout](../../../../packages/client/ui-layout/README.md) owns geometry.** AppFrame grows a fourth track (`sidebar | center | details | sidepanel`) with the concession chain extended in contract order — details shrinks then auto-closes first, then the side panel shrinks then auto-closes; the side panel outranks details because it hosts ongoing side work while details is a transient inspection. New constants (`SIDEPANEL_MIN/MAX/DEFAULT` = 320/720/420, wider than details for terminal use), a new drag handle reusing the details pill pattern, and a `sidepanel` child slot (single, `session-maybe`, like the conversation column — it keeps identity across session switches and is not session-gated). The layout store adds `sidepanel` width plus open/close/toggle actions, and flips from transient to persisted (`localStorage` key `dsh.layout`): dragged widths and open/closed preferences now survive reloads, with the viewport-derived narrow pair self-correcting on mount. `ctx.layout` gains `toggleSidepanel`/`openSidepanel`/`closeSidepanel`.
- **[ui-sidepanel](../../../../packages/client/ui-sidepanel/README.md) owns the workbench.** One package registers the shell into the layout's `sidepanel` slot and declares two seats inside it: `sidepanel.launchpad` (list — bookmark cards) and `sidepanel.app` (keyed by app id — tab bodies). The persisted per-session workbench store (`dsh.sidepanel.workbench.<sessionId>`) keeps a recursive tree of tab groups and horizontal or vertical splits. Tabs can be reordered or merged by dropping in a strip and split left, right, top, or bottom by dropping on a pane edge; closing an empty non-root group collapses its branch. The closest edge selects the split direction, while a five-target docking guide and live placement overlay make the result visible before drop. Pointer and keyboard-adjustable dividers keep 10% of the adjacent extent on each side. With no tabs open — or via the + button — a group renders the launchpad. Every open app is mounted once in a stable root layer and positioned over its group, so both inactive tabs and tabs moved across groups retain terminal connections and view state. The shell gives each app the full group content rectangle without padding or card chrome; apps own their own insets. The flat, continuous tab strip supports arrow/Home/End navigation and middle-click close. A session-header utility entry contributes the rightmost toggle. A new app is two registrations (one launchpad card + one keyed entry) with zero shell edits; the tab title is frozen at open time (launchpad copy supplies it).
- **The shipped `/btw` app is a pure client view over the durable log.** Its transcript derives from the conversation nodes snapshot — one row per `command`-kind node named `btw` (question from logged `command/run` args, answer from the `command/done` outcome, pending while the pairing is open) — and its input submits `/btw <question>` through the host `command.execute` RPC, the same wire the composer uses. The side panel never talks to a model or subagent; whatever `/btw` implementation is composed answers.
- **The terminal is a human attachment to the existing PTY capability.** `dsh-terminal` exposes an Agent-scoped generated Remote namespace for eligible backend discovery, named attach/resume, bounded cursor reads, raw input, resize, and close. `terminal-bash` adds a bounded raw VT stream alongside its unchanged sanitized model output; human presentation starts the operating-system account's login shell without model-only prompt or pager overrides, while explicit human-shell config can replace that choice and model presentation retains controlled Bash. `subprocess` supplies optional PTY resize and preserves the caller's effective `TERM` as the PTY terminal type. The Client loads `ghostty-web` only after the retained tab body has non-zero geometry and uses its embedded libghostty-vt WASM core to render the stream. The terminal surface is the undecorated canvas, without a connection/backend toolbar or inner card chrome. Because `ghostty-web` makes its host editable for keyboard input, the shell suppresses the browser's native caret and leaves cursor rendering to libghostty-vt. The Client supplies the primary device attributes response omitted by the pinned renderer only when the renderer did not answer, which lets login shells complete terminal capability detection without a timeout. The Host continues to own sandbox policy, Agent authority, output bounds, and process-tree teardown. Browser-safe Remote payloads live in `dsh-terminal/remote-types`, so the Client program never imports Host-only `Agent` or Node types.
- **Each client carrier declares the terminal's startup requirements.** The side-panel Client injects the exact `remote.terminals` service it reads. In the Web bundle, the module and HMR plugins wait for `webServer`, so their index tap and carrier are active before the Client module graph starts. The desktop patch replaces that activation dependency with `desktopRuntime`, because Electron reads the module graph and bundle paths without an HTTP server. The Web CSP permits `data:` fetches and `wasm-unsafe-eval` for `ghostty-web`'s embedded WebAssembly module without enabling JavaScript `eval`.
- **The blank-panel fault is fixed at the slot framework seam.** A `session-maybe` entry deliberately keeps the same React incarnation while its blank state adopts the first Session. A declared store therefore must also keep an always-callable selector Hook in that blank state; omitting it made `SidePanelRoot` call one additional Hook after adoption and React rejected the render. `PropsStoreFor` now represents the maybe-store face, `web-react` supplies a stable maybe selector Hook before a Session exists, and actions remain absent until the store does. A real registry/renderer full-chain regression covers blank-to-first-session adoption.

## Alternatives considered

- **Reuse the details column as the side panel host** — rejected: details is session-gated, 300–520px, and auto-closes on session switch; a terminal needs width and continuity, and taking the slot over would displace tool-call details rather than compose beside it.
- **Discover launchpad entries from the keyed registry** — rejected: the slot system exposes no registration metadata to occupants, and enumerating entries for labels would be a second read path; instead each app registers one launchpad card (its own copy, its own glyph) plus its keyed body, keeping routing authority at register sites.
- **Use xterm.js like the reference sidebar** — rejected: its tab lifecycle and zero-size-mount lessons apply, but this integration explicitly requires libghostty WASM. `ghostty-web` supplies the libghostty-vt parser with an xterm-compatible terminal API, so the Host transport remains renderer-independent.
- **Render app bodies directly inside recursive group leaves** — rejected: moving a tab to another leaf would replace its React subtree, closing an attached terminal and discarding local view state. A stable root app layer separates component identity from split-tree geometry.
- **Persist only the side panel width** — rejected: one geometry fact would then have two homes (a live value in the layout store, a durable preference elsewhere). Persisting the whole layout store keeps one home and improves sidebar width durability with it; the transient contract was a README-documented decision, updated in the same change.

## Consequences

- Two right columns can be open simultaneously; the concession chain decides squeezing deterministically, and center always keeps `CENTER_MIN` until the final fallback.
- The `/btw` exchange is visible in both the conversation (generic command card) and the side panel tab — one durable record, two views; the side tab additionally offers the ask input.
- The tab-group and split tree is per session (store scope follows the session-maybe entry): switching sessions swaps workbenches; each Session's arrangement persists across reloads via the scoped key.
- Closing a terminal tab or switching its Session closes and joins that Agent's attached PTY; activating another tab or moving the terminal across groups leaves it mounted and connected.
- `terminal-bash` is disabled in the Windows Web composition until the Windows PTY provider can meet the same interactive and process-tree guarantees.

## Verification

`ui-layout`: solver specs cover the two new concession steps (details-before-sidepanel ordering, four-track seams, pure recovery), store specs cover the side panel action set plus persistence round-trip, and AppFrame specs cover the fourth track, its handle, session independence, and concession. `ui-sidepanel` covers the four edge-split directions, five-target preview state, center merge and reorder, empty-branch collapse, divider resizing, persisted tree state, launchpad routing, stable app identity across a browser drag, keyboard and middle-click gestures, `/btw`, every Terminal Remote adapter, the undecorated libghostty lifecycle, native-caret suppression, split primary-device-attributes queries, and a full registry/renderer blank-to-session render. `web-react` separately pins the always-callable maybe-store Hook. Terminal service/backend tests cover authorization, attach/resume/rollback, request bounds, raw stream truncation/cancellation/final state, raw input, account-login-shell selection and explicit override, human `TERM`, PTY terminal-type propagation, resize, and cleanup. The Web replay opens the real assembled launchpad, loads and connects the libghostty terminal, exercises the Trajectory and Session log apps, and asserts that no slot, page, or console error occurs.
